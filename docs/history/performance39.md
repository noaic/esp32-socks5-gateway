# perf39：发送缓冲 23040 字节折中

diag37 使用17280，单路13.45/11.54、四路20.47/18.77 Mbps。perf38 使用34560，单路16.13/14.04、四路21.29/19.04，但驱动 memory 返回显著增加到约7%/11%，不作为稳定优化。数据来自一组三轮，背景活动会话数不同，仍需要重复验证。

本候选仅将 sdkconfig 中 CONFIG_LWIP_TCP_SND_BUF_DEFAULT 改为23040，即16×1440 MSS，较稳定基线增加5760。它恰好与现有接收窗口大小相等，但这不是TCP对称窗口的协议要求，也不保证最优。8KiB应用队列、接收窗口、64TCP/32UDP、无线缓冲、任务绑定、diag37观测均不变。默认配置仍17280，候选待测。

目标是减少17KiB额度造成的ACK等待限制，同时避免34KiB额度下的过大突发。64路双向TCP最大新增payload额度理论为737280 bytes，实际按流量动态分配，另有segment等开销。比34KiB候选风险更小但仍可能增加延迟和驱动压力，需实测。

原 http://192.168.1.10:18080/bench 页面标签 perf39-sndbuf23k，单路后四路，数据自动保存。重点比较吞吐、flight、snd_buf零值、unsent、驱动返回和TCP重传。若收益不足或压力仍大则回退17280；不继续无依据扩Wi-Fi buffer。

## 第一组结果与回退

完整CPU窗口单路2个、四路8个，Core1 idle中位24.4%/7.3%，proxy37.45%/40.2%，tcpip34.95%/49.7%。四路活跃会话13–15，diag37为33–35。四路内部空闲最低106487、最大块59392、PSRAM最低6811824；没有堆逼近耗尽。

四路前后相邻driver采样：AP134144次中memory返回10500（7.83%），STA134842次中11639（8.63%）；实际采样含测试边界，不是最终丢包率。驱动压力仍明显高于原17KiB基线约0.1%，没有达到预期折中。TCP新增客户端fast1、上游RTO1。两侧flight能到23040，snd_buf零值及unsent排队仍出现，扩大额度没有消除全部背压。

决定：恢复17280，保留diag37观测布局做一次回到基线的复测；不采用23040或34560为稳定配置。若回退后驱动压力随之下降，才更有依据判断扩容和发送突发的关系；若不下降，继续检查环境变化，避免过度归因。本轮自动结果、UART和analysis.json保存于快照。
