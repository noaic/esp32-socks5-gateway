# diag37：select 等待分布与 TCP 窗口采样

本轮补齐此前没有完成的观测。保持稳定版的无线、TCP 窗口、8 KiB 双向队列、任务绑定、socket 参数和收发次数。AP 本地 HTTP 测速仍关闭；只恢复 WSL 上原来的 192.168.1.10:18080 测试服务。

`CONFIG_PROXY_PIPELINE_DIAG` 默认关闭，当前诊断构建开启。仅统计目标 192.168.1.10:18080、状态 RELAY、已有 payload 且最近一秒有活动的会话。最后一秒可能包含测试边界和空闲 keep-alive，分析时与自动保存的测速时间对齐。

每次 select 记录完整调用墙钟时间、最大值和五档计数：小于 100 us、100 us–1 ms、1–5 ms、5–20 ms、至少 20 ms。记录 timeout/error、进入 select 时有待发队列和无待发队列的等待时间、两方向待发字节峰值。FD 集合仍包含其他连接，所以等待不能全部归因于某一个测速连接；定时器包括任务调度，并非独占 CPU 时间。原 100 ms timeout 是最大等待，不是每个数据包固定等待 100 ms。errno 在计时后恢复。

每 250 ms 最多请求一次 TCPIP callback，轮换当前活跃测速流。回调只读取 TCP PCB，禁止 UART 打印、主动 ping 或修改 PCB。客户端侧以 local port、映射后的 peer port 和 client IPv4 匹配，上游侧以独立 local port 与 SOCKS remote port 匹配。独立诊断对象通过 busy release/acquire 发布结果，单个 proxy worker 请求和消费，未消费结果不覆盖。不写 flow metadata 到 PCB。

两侧分别汇总 snd_wnd、cwnd 的最小值与均值，snd_buf/rcv_wnd 最小值，flight 的平均和最大值、unsent/unacked 字节峰值、窗口/缓冲为零次数、flight 达到 min(cwnd,snd_wnd) 的次数。flight 是 snd_nxt-lastack 的序列差，未测 RTT；窗口达到限制只描述瞬时状态，不自动证明吞吐归因。PCB 在请求后关闭会报告 missing。callback_wait_us 是请求到回调开始的调度延迟。每 10 秒从 proxy worker 输出并清零汇总，callback 可能跨汇总边界。

新增固定统计对象约 368 bytes（272+96，来自目标 ELF）；没有新 task、socket 或 payload 缓冲。采样和活跃过滤仍有 CPU 开销，因此该固件用于定位，不直接作为提速候选。主机 15 项生产 TCP relay 回归通过，但它们编译 POSIX 路径，不能代替 ESP 诊断分支的实机验证。ESP 编译验证开启分支；实机需要单路和四路完整内容校验及日志检查。

测试：Android 接 AP，暂停其他下载，打开 http://192.168.1.10:18080/bench ，页面应显示 diag37-pipeline。先单路、再四路，前端结果由 WSL 自动保存。不依赖 Android 数字抄录。分析后只针对明确证据做单变量候选，未发现异常则关闭该诊断配置。

诊断实现、主机回归和实机单路/四路采样已完成。采样用于解释瓶颈，不宣称其本身提高带宽。

## 第一组实机数据

2026-10-04 14:23–14:25，单路三轮下载/上传 13.62/11.11、13.45/11.54、13.14/11.71 Mbps，中位 13.45/11.54；四路总吞吐 20.47/18.81、20.41/18.48、21.02/18.77，中位 20.47/18.77。前端下载全字节、主机上传 SHA 校验通过。完整自动成绩和时间对齐分析保存在 diag37 快照。

测速期间汇总输出的 select 均值单路约 2.63 ms、四路约 2.66 ms；四路所覆盖的汇总没有 timeout/error，多数落在 1–5 ms。窗口汇总含边界，因此分布不视为逐传输精确值。select 内部有 socket 状态扫描和 mutex，不将 2.66 ms 解释为全部睡眠，更不能直接通过减少 100 ms timeout 解决。

完整 CPU 窗口单路 Core1 idle 中位 10.0%、proxy 55.1%、tcpip 31.4%；四路 Core1 idle 1.25%、proxy 44.9%、tcpip 51.2%。测试过程中背景/保活会话约 32–35，因此不与历史约 12 活动会话的数据做严格 CPU 效率对比；diag37 活跃过滤/每循环统计也增加观察成本。四路确认接近满载，单路也有较高 proxy 开销。

客户端 peer window 固定 65535，上游约 63–65 KiB；正流量侧 cwnd 可到约 64 KiB，而 flight 最大 17280，与发送缓冲上限一致，发送缓冲零值在部分样本出现。flight_at_limit 为零，未观察到对端零接收窗口。ESP 自己的 rcv_wnd 偶尔为零，反映接收背压而非上游广告窗口为零。callback 调度通常 28–49 us，未失败，无缺失 PCB，不能证明不存在稀有延迟。driver TX memory 错误有少量增长，不能宣称驱动全程零错误；未新增 TCP RTO/fast、数据校验失败。

这些数据支持试验增大发送缓冲，但不证明它是唯一瓶颈。下一候选 perf38 保留所有诊断布局，仅把 lwIP 默认发送缓冲从 17280 改为 34560，观察吞吐、flight、snd_buf 零值和接收背压是否改善。若结果混合或资源压力增加则回退。

## 完成发送缓冲对照后的结论

依次测17280、34560、23040，再回到17280；每项单路/四路各三轮，自动保存并校验内容。下载/上传中位数（Mbps）：

| 发送缓冲 bytes | 单路 | 四路总吞吐 |
| --- | --- | --- |
| 17280，首次 | 13.45 / 11.54 | 20.47 / 18.77 |
| 34560 | 16.13 / 14.04 | 21.29 / 19.04 |
| 23040 | 14.43 / 14.62 | 18.54 / 17.73 |
| 17280，回退复测 | 14.02 / 13.66 | 20.17 / 19.31 |

相同代码的单路上传也波动约18%，且背景活动会话数不同，不能把候选的单路提升全部归因于扩容。四路没有稳定的整体收益。扩大缓冲时驱动 memory 返回约7–11%，回退复测AP约0.73%、STA约0.90%，初测约0.1%；这是API调用返回比例，含前后相邻采样边界，不是无线最终丢包率。回退单路没有此类返回；测试结束时两侧累计RTO/fast仍为零。

回退四路完整CPU窗口的Core1 idle中位6.8%、proxy_tcp38.8%、tcpip53.0%；内部空闲最低104827 bytes、最大块55296、PSRAM最低6836504。peer接收窗口没有证据表明是主要限制，持续负载下Core1资源更紧；发送额度限制flight存在，但单纯放大额度会加大驱动压力。select墙钟分布不能定位到具体CPU热点，下一项若继续，应测socket扫描/锁、复制、lwIP处理的函数耗时，再决定是否改事件循环，不能据此宣称硬件达到绝对上限。

保留17280，结束本轮参数试探。诊断代码保留为可选开关，日常构建关闭CONFIG_PROXY_PIPELINE_DIAG，与defaults一致，不增加任务。原始结果、串口和时间对齐analysis.json位于build-snapshots/diag37-return17k；perf38、perf39各有独立快照。本轮没有采纳新的带宽参数。
