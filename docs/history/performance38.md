# perf38：lwIP 发送缓冲单变量对照

基线 diag37 单路 13.45/11.54 Mbps、四路总吞吐 20.47/18.77 Mbps，三轮全部内容校验通过。两侧对端窗口约 64 KiB、活跃方向 cwnd 可超过 17280，而 flight 峰值和 snd_buf 耗尽提示默认发送缓冲是可检验限制。四路 CPU1 接近满载，因此不承诺扩容会提高总吞吐。

唯一候选参数：当前 sdkconfig 中 CONFIG_LWIP_TCP_SND_BUF_DEFAULT 17280→34560。sdkconfig.defaults 保持稳定值 17280。保持 23040 接收窗口、8 KiB 应用队列、64 TCP/32 UDP 上限、Core1 TCPIP/proxy、Wi-Fi TX32/AMPDU/40 MHz 和 diag37 观测不变。没有旧版 TCP_SNDBUF API 猜测或全局 SDK 源码修改。

本机 6.1 Kconfig 合法范围不启用 window scale 时 2440–65535。该参数定义每个 PCB 的发送字节额度，并影响默认发送队列额度；并非预先为每条连接分配 34560 字节。UDP association 的 TCP 控制连接也采用该默认值，但平时只发送少量控制字节。payload/segment/pbuf 和系统分配的实际增长需读实机 heap，不能只把空闲 PSRAM 当作内部内存余量。

64 路双向 TCP 如果都填满，增加的 payload 额度理论可达 64×2×17280=2211840 字节，另有分段等开销；这不是固定分配或所有应用同时发生的内存用量。四路实验先核对最低内部空闲、最大连续块、PSRAM、driver memory 错误、TCP 重传和内容校验。发送队列扩大可能增加突发和延迟。关闭 TCP 或改变状态仍由 lwIP 和原 worker 处理，不调整协议重试策略。

测试保持原 WSL 地址和端口，页面标签 perf38-sndbuf34k。先单路再四路，结果自动存入 bench-perf38-results.jsonl。需与同一诊断布局的 diag37 比较，历史 perf29 作为参考。还没有实机成绩，候选不当作稳定优化。

## 第一组结果与折中决定

单路 14.95/14.44、16.13/14.04、18.15/13.51 Mbps，中位 16.13/14.04，较 diag37 中位约 +19.9%/+21.7%。四路 18.66/19.04、21.29/19.04、21.48/18.97，总吞吐中位 21.29/19.04，约 +4.0%/+1.4%。内容校验均通过，但只有一组，不能宣布稳定提升。候选四路活动会话 16–24，基线 32–35，背景/保活数量不同影响 CPU/吞吐，不能将全部差值归因于缓冲。

PCB 采样客户端 flight 峰值 34560，上游 23488，较原 17280 确实增加；候选四路 client/upstream 的 buf_zero 为 4/0（各299样本），基线 8/5（各293样本）。上游/客户端 unsent 峰值 14848/27360，增大额度后更多数据排在 TCP 层。Core1 idle 中位单路 19.2%、四路 4.6%；背景差异和窗口边界限制精确 CPU 对比。

四路相邻驱动采样差值 AP 132545 次中 memory 返回 9501 次（7.17%），STA 133677 次中 14504（10.85%）；基线约 0.107%/0.097%。这些是 API 返回压力，含时间边界，不是 MAC 重试率或最终丢包率。新出现客户端 RTO2/fast6，上游均0。没有全局断流或内容校验失败，但发送压力显著增大，暂不将34560列为稳定配置。

单路/四路内部空闲最低100383/101031，最大块57344，PSRAM最低6933048/6846448；未见堆容量逼近或分配失败。不能将 driver 的 memory 返回归因为系统 heap 耗尽，它也可能是发送缓冲/队列压力。下一候选只将发送额度折中到23040，不改Wi-Fi队列或增加本地输出重试。保存本轮分析到快照 analysis.json。
