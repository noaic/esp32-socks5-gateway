# 带宽优化结论（2026-10-04）

更正：此前收尾没有新增 select 等待分布和 TCP 窗口采样。下述空队列和高 idle 多来自轻载/空闲窗口，不能用于排除满载瓶颈。diag37 已补齐观测并完成17280→34560→23040→17280发送缓冲对照，详见 [diagnostics37.md](diagnostics37.md)。四路复测20.17/19.31 Mbps，Core1 idle中位6.8%；扩大缓冲没有稳定整体收益，driver memory返回却明显增加，因此保留17280并关闭可选pipeline采样。不能宣称到达硬件绝对极限。

此前已有观测：

- 实际代理运行日志中 `queues c2s_flows=0 bytes=0 s2c_flows=0 bytes=0`，没有持续待发数据。
- 轻载/空闲 CPU 采样中 Core 0/1 的空闲率约为 95% 以上；四路吞吐测试 Core 1 仅约 2%–7% 空闲。
- 上述历史采样的相关错误为零，不能外推到所有负载。diag37回退复测没有新增TCP RTO/快速重传，但四路driver memory返回AP约0.73%、STA约0.90%；该API返回比例不等于最终丢包率。
- AP 和 STA 都协商到 40 MHz；STA RSSI 约 -31 至 -34 dBm，客户端 RSSI 约 -16 至 -21 dBm。
- 单路 AP 本地和 STA+SOCKS 端点约 27 Mbps，而完整 AP→代理→STA 单路约 13 Mbps；历史四路总吞吐约 20–23 Mbps。这个差异符合双向 Wi-Fi 共享空口、ACK/窗口节奏和代理转发调度的叠加影响，不能归结为某一个缓存值。

本轮发送缓冲候选均未采纳，接收窗口、队列深度、AMPDU和Wi-Fi缓冲保持原配置；临时测速服务在收尾时关闭。继续研究应对满载时socket扫描/锁、复制和lwIP处理做函数级profiling，以区分CPU开销和空口限制。单射频AP+STA共享空口是明确的拓扑约束，但现有测量不能量化其独立贡献；若追求大幅提升，再比较独立AP或有线上游的硬件方案。
